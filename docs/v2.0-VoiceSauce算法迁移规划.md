## 一、语言选型评估（计算效率）

算法画像：逐帧信号处理（FFT / 倒谱 / 自相关-LPC / 递推滤波 / 逐帧循环），单文件 10⁵–10⁶ 样本，帧数 10²–10³，帧内 FFT 512–4096 点。**没有超大规模矩阵运算，也没有实时约束**——瓶颈天然在 FFT 与滤波，这两者库实现都是 C 速度。

| 方案 | 单文件速度 | 批量吞吐 | 与后端集成 | PyInstaller 打包 | MATLAB 语义对齐 | 维护/调试 |
|---|---|---|---|---|---|---|
| 纯 Python 循环 | 慢 10–100× | 差 | 无摩擦 | 小 | 易 | 易 |
| **NumPy/SciPy 向量化（推荐）** | 接近 C（FFT/滤波走 C 底层） | 好，可再加进程池并行 | 零摩擦（server.py 即 Python） | +40–60MB，路径现成 | 中（索引/round 陷阱可控） | 易，交互可查中间量 |
| Numba JIT | 极快 | 极快 | 零摩擦 | +150MB+，打包是坑 | 中 | 中（JIT 报错难读） |
| C/C++ 扩展 | 最快 | 最快 | 需 FFI | 小 | 难（维护两套代码） | 难 |
| Rust→DLL | 最快 | 最快 | 需 FFI | 小 | 难 | 难 |
| C#/.NET | 快 | 快 | 需 IPC/FFI | 需运行时 | 中 | 另起一条技术栈 |

**推荐：NumPy/SciPy 向量化 + 帧矩阵化 + 多进程并行。理由：**

1. **效率来源在结构，不在语言**。MATLAB 代码里逐帧循环翻译成「帧堆叠成矩阵 → 一次性 batched FFT/滤波」后，NumPy 底层即优化 C（pocketfft / BLAS / C 实现的 lfilter）。经验上向量化后与手写 C 差距 < 2×。
2. **吞吐估算**：单文件全参数集（F0+Formant 除外）预计 < 1 s；批量 100 文件在进程池（CPU×N）下分钟级。对照：现 v1.2 走 Praat 是单进程单线程跑全批。迁移后吞吐不降反升。
3. **逐行复刻的开发效率权重最高**。本项目第一目标是「数值忠实于 MATLAB」，Python 交互式调试中间量、matplotlib 即时看谱，比 C/Rust 快数倍，出错成本低。
4. **渐进升级路径**：若个别算法（shrp）实测慢，可局部加 numba 或 cffi，不动架构——不必一开始背包袱。

结论：**主体 Python(NumPy/SciPy)；F0/Formant 例外（见下）**。纯效率上 C/Rust 最快，但本项目效率不是瓶颈，忠实性、可维护性、打包成本才是，故不选。

## 三、架构

```
ps-shell/backend/pysauce/          ← 新包，纯算法，无 I/O 副作用
  matlang.py        ← MATLAB 语义桥：round(四舍五入远离零)、1-based 索引辅助、remap
  framing.py        ← 读 wav、帧切分、frameshift/Nperiods_EC 语义（vs_Initialize 默认值）
  get_energy.py     ← func_GetEnergy.m（文件头注明蓝本文件+版本+关键行号）
  correct_iseli.py  ← func_correct_iseli_z.m
  get_bw_fmt.py     ← func_getBWfromFMT.m
  get_h1_h2_h4.py   ← func_GetH1_H2_H4.m（含 A1–A3、2K/5K 调用）
  get_2k_5k.py      ← func_Get2K/Get5K/GetH42K/Get2K5K
  get_cpp.py        ← func_GetCPP.m
  get_hnr.py        ← func_GetHNR.m
  get_soe.py        ← func_getSoE.m
  shrp.py           ← shrp.m（对齐 v1.37；现有 measures_extra.py 的 SHR 升级收编）
  pickpeaks.py      ← func_pickpeaks.m
  engine.py         ← 调度：与 praatSauce.praat 等价的文件级编排（帧序→各算法→行向量）
  output_cols.py    ← 按 func_getoutputparameterlist.m 对齐输出列名
```

- **server.py**：`/api/run` 增加 `engine` 字段（`praat` | `pysauce`）。向导不传 → 默认 praat（行为零变化）；vs.js 界面传 pysauce。
- **engine 循环**：读 wav →（可选重采样/声道）→ 帧 timebase（1 ms frameshift）→ F0/Formant 调 Praat（复刻 praatF0/praatformants 语义）→ 其余算法纯 NumPy → 合成与 v1.2 相同结构的行 → 复用现有输出/导出管线。
- **共享中间量**：帧切分、窗、F0 向量全算法共享一次（MATLAB 原版同样共享 variables/F0），省时且保一致性。
- **进度**：纯 Python 循环逐文件回调现有 watch 机制，Praat stdout 缓冲问题消失。

## 五、验证策略（无 MATLAB Runtime 的替代锚）

1. **逐行复刻 + 中间量断言**：翻译时每个 MATLAB 段落在 Python 侧保留中间量检查点，合成信号下手算锚点。
2. **opensauce-python 交叉验证**（Apache-2.0，官方 Python 移植，宣称对齐 VoiceSauce v1.25）：同批样本同参数输出对比，出容差表。v1.37 与 v1.25 的算法差异以源码 diff 为准说明。
3. **文献数值范围 sanity**：正常语音 HNR05 ≈ 0–20 dB、CPP ≈ 0–20 dB 等区间检查，防系统性错位。
4. **v1.2 Praat 引擎对照**：仅作参考报告（等价项≈3），不作为对齐目标。
5. **端到端回归**：samples/ 30 wav 的输出表快照进 `tests/`，任何改动可回归。

## 五之三、两界面数据互通（2026-10-26 用户提出，硬性）

> **用户原话**："两个界面的数据结果格式应该互通，可以彼此直接调用。比如我在向导界面用 praat 做好了 f0 和共振峰，那么到 vs 界面，这些数值就可以直接利用来计算其他参数。"
> **反过来亦然**："vs 界面比如用 snack 做的共振峰，应该可以在向导界面中直接使用。"

| 机制 | 实现 | 卡 |
|---|---|---|
| 共用目录 | 两者都读写 `<音频目录>/measure/` | F1 §0b |
| **对象后缀分引擎** | Praat → `.Pitch`/`.Formant`（**Praat 文本格式，与 1.2 完全一致**）；Snack → `.sF0`/`.sFormant`；STRAIGHT → `.strF0`。**非 Praat 引擎绝不写成 Praat 对象格式**（伪造对象=语义错）。后缀唯一定义在 `review_export.ENGINE_OBJECT_EXT` | F1 §0b / F5 |
| 复用开关 | `pitchRead`/`pitchReadDir`/`formantRead`/`formantReadDir`（1.2 已有，params_schema L260-273） | F1 §0b / F2 |
| 格式读写 | Praat 走 `praat_objects.read/write_pitch_text`、`read/write_formant_text`；非 Praat 走自有简单格式（`# engine=… dim=…` 头 + `time<TAB>value` 行） | F1 §0b |
| 基准引擎 | `F0algorithm`/`FMTalgorithm`（VS 原生机制，func_parseF0/parseFMT）；向导第三步 UI 见 F5 卡 | F1 §0c / F5 |
| 引擎差异标注 | 结果分列（pF0/sF0/strF0）+ 界面来源标注 | F3 |

⚠️ **本声明推翻早前的"两引擎产物分目录"设想**（见下 §六 风险行已修正）：2.0 的 F0/Formant **必须与 1.2 同目录同格式**（Praat 那套），否则互通不成立；非 Praat 引擎用**同目录、带引擎后缀**的独立文件，既不互踩也不破坏 Praat 口径。

**向导第三步的基准引擎选择**（2026-10-26 用户追加）：向导页第三步新增「其他参数的基准引擎」卡，F0 与共振峰**两组独立单选**，默认 Praat；选项按 `measure/` 里实际存在的对象动态启用/置灰；三套都没有则硬拦批量。详见 F5 卡。
