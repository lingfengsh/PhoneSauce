1. 一句话看清全貌

这个软件自己不做任何声学计算。它只做三件事：

  1. 把你点的几个选项，翻译成 Praat 认识的参数表（params.csv）；
  2. 启动 praat.exe，让它去跑 praatSauce.praat；
  3. 把 Praat 吐出来的大表，翻译成人能看的曲线、诊断和导出文件。

真正的算法（基频、共振峰、谐波幅度、HNR、CPP……）全部来自上游项目 praatSauce 1.0.8，作者是 James Kirby 和 Rasmus Puggaard-Rode。这个壳子的价值不在算法，而在把 55 个参数、一堆路径和 Praat 的怪脾气，包装成五步向导。

三层分工

层代码在哪角色负责什么绝不做什么
前台ps-shell/ui/挂号台 / 问卷 显示、收集选项、画曲线、翻页不读文件、不算数、不碰 Praat
后台ps-shell/backend/护士 / 调度员 校验参数、写单子、起进程、读结果、做诊断不做信号处理
化验室praat.exe + scripts/*.praat检验科 真正算 F0、共振峰、谐波、噪声不知道界面存在，只认参数文件
比喻：体检中心 你到体检中心，先在前台填问卷（界面）；护士把你的要求誊到一张检验申请单上（params.csv）， 然后把你领到抽血窗口（Praat）；化验室只认那张单子，不认你说了什么； 报告出来后，护士先帮你核对一遍有没有明显异常（诊断）， 再由医生抽查几张片子（九宫格复核）；最后装订成册交给你（导出）。
图 1：五个步骤与唯一真正干活的 Praat。界面只负责收集与展示，计算全在下面那个框里。
这一节你该记住的 这个软件是翻译官 + 调度员，不是分析算法。你以后遇到任何"结果不对"的问题，第一步都该问： 是单子写错了（参数），还是化验室做错了（Praat 参数/版本），还是报告读错了（统计口径）？这三层对应完全不同的排查方向。

2. 启动：双击之后发生了什么

对应文件：ps-shell/app.py（248 行）

双击 PraatSauceShell.exe（或源码态跑 python ps-shell/app.py），程序走四步：

settings.ensure_dirs()                 # 1. 准备目录
srv = server.start_server(0)           # 2. 起一个只监听本机的服务
port = srv.server_address[1]           #    端口是系统临时分配的
url = f"http://127.0.0.1:{port}/launch.html"   # 3. 拼出地址
mode = "window" if getattr(sys, "frozen", False) else "browser"  # 4. 选窗口还是浏览器

2.1 为什么端口写 0

start_server(0) 里的 0 不是"第 0 号端口"，而是告诉操作系统：随便给我一个空着的端口。这样不会撞上你电脑上已经跑着的其他服务。真正的端口号启动后才拿到，所以地址是拼出来的，不是写死的。

2.2 为什么是 127.0.0.1

127.0.0.1 是"本机回环地址"，只有这台电脑自己能访问。换成 0.0.0.0 就意味着同一局域网里的人也能打开你的界面——对于一个能读写你硬盘文件、还能启动进程的程序来说，这是不能接受的。

2.3 三级兜底：窗口起不来怎么办

顺位做法什么时候会退到下一级
1pywebview + WebView2 独立窗口没装 WebView2 运行时、或 pywebview 导入失败
2Edge 的"应用窗口"（--app=，没有地址栏）找不到 msedge.exe
3系统默认浏览器前面都失败；此时会弹一个系统消息框说明原因
比喻 这就像去一家只收现金的店：先试刷卡，刷不了试扫码，都不行才让你去隔壁取钱。目的只有一个——别让用户双击之后"什么都没发生"。

源码态（你在仓库里跑）默认走浏览器，是为了改完界面刷新就见效；打包后的 exe 默认走窗口，是因为对方的电脑上装的是 360、QQ 浏览器还是旧版 IE，你控制不了。

2.4 浏览器模式下的"心跳"

浏览器模式有个副作用：你关掉标签页，Python 进程还活着，任务管理器里就多一个孤儿进程。解决办法很土但有效——页面每 5 秒给后台报一次"我还在"，后台发现超过 60 秒没动静就自己退出：

IDLE_TIMEOUT = 60
while True:
    time.sleep(5)
    if time.time() - server.LAST_PING["t"] > IDLE_TIMEOUT:
        break        # 关标签页 60 秒后，服务自行退出

2.5 门禁：为什么本地网页还要令牌

你打开任何一个网页，那个网页都能向 127.0.0.1 发请求。如果这个本地服务不设防，恶意网页就能悄悄让你的电脑跑一批 Praat、甚至读写文件。所以启动页 launch.html 会先给你种一张"门禁卡"（Cookie PS-Token），之后每个请求都必须带着它。后台每次先查三样东西：

host = (self.headers.get("Host") or "").rsplit(":", 1)[0]
if host not in ("127.0.0.1", "localhost"): return False   # 防 DNS rebinding

origin = self.headers.get("Origin")
if origin and urlparse(origin).hostname not in ("127.0.0.1", "localhost"): return False

tok = self.headers.get("X-PS-Token") or cookie 里的 PS-Token
return tok == TOKEN
这一节你该记住的 "本地网页应用"不是网站。它借浏览器当画布，数据和计算全在你自己的电脑上。 端口随机 + 只绑本机 + 请求带令牌，是这类程序的三条基本安全线。

3. 界面：五个抽屉

对应文件：ps-shell/ui/index.html（约 1900 行）、app.js（约 3600 行）

整个界面没有用 React、Vue 这类框架，就是一个 HTML 文件加一堆原生 JavaScript。五个步骤在 HTML 里就是五个 <section class="step-panel">，它们是同时存在的，只是被 CSS 藏起来了。

<section class="step-panel" data-panel="1"> ... 选音频 ... </section>
<section class="step-panel" data-panel="2"> ... 要测什么 ... </section>
<section class="step-panel" data-panel="3"> ... 批量运行 ... </section>
<section class="step-panel" data-panel="4"> ... 查看结果 ... </section>
<section class="step-panel" data-panel="5"> ... 导出数据 ... </section>

3.1 翻页只做三件事

控制翻页的函数叫 setStep(n)，一共三十来行，核心就三句：

function setStep(n) {
  state.step = n;

  // 1. 只显示第 n 个抽屉
  $$(".step-panel").forEach(p => p.classList.toggle("hidden", +p.dataset.panel !== n));

  // 2. 点亮左侧步骤条，并把地址栏改成 #step=3（刷新后还停在这一步）
  history.replaceState(null, "", "#step=" + n);

  // 3. 触发这一步专属的刷新
  if (n === 2) renderPresets(), renderParams(), renderMeasurePicker();
  if (n === 3) { runPrecheck(); renderRouteSwitch(); refreshReviewState(); }
  if (n === 4 && window.refreshResultsGrid) window.refreshResultsGrid();
  if (n === 5) refreshExpParams();
}
一个容易忽略的设计 界面不保存任何真数据。你每次进入第 4 步，它都会重新向后端要一次网格数据； 进入第 5 步，重新要一次可导出的列清单。 这样做的好处是"界面永远是后端状态的快照"，不会出现界面显示的和磁盘上的不一致。 代价是每次翻页都要多一次请求——在本地服务上，这个代价可以忽略。

3.2 为什么不用框架

三个原因，都很实在：

  • 离线可用：打包后不能依赖 CDN，框架得整个塞进包里，体积翻几倍；
  • 调试直观：改一行 CSS 刷新就见效，不需要编译；
  • 维护者只有一个人：框架带来的抽象，在单人项目里往往是负债。
这一节你该记住的 "五步向导"在代码里只是五个被隐藏的区块 + 一个切换函数。 复杂的不是技术，是把每一步该显示什么、该刷新什么想清楚。

4. 参数：整个软件的"菜单"

对应文件：ps-shell/backend/params_schema.py（约 900 行，97 条定义）

这是整个项目最重要的一个文件，作者在开头就写了：

"""praatSauce 参数元数据。
这是整个 GUI 的单一事实源：界面控件、校验规则、预设方案、CSV 生成
全部由这里驱动。字段名必须与 praatsauce 的 params.csv 完全一致。
"""

4.1 一条参数长什么样

它不是"配置"，而是"描述"。每条参数都在描述自己：叫什么、什么类型、归哪一组、给谁看、默认多少、中文怎么解释。

dict(name="f0min", label="基频下限", type="number",
     group="pitch", tier="novice", default=60,
     help="低于这个值的声音不会被当成基频。男声一般 50–75。")
字段作用例子
name必须和 params.csv 第一列一模一样，这是两边对话的暗号f0min
type决定界面长什么样、怎么转成文本dir / file / text / int / number / bool / choice
group归到哪一类，决定界面上的分区io / measures / pitch / formant / textgrid / advanced
tier新手档还是进阶档novice / advanced
help鼠标悬停时那句人话解释"男声一般 50–75"
cols这条参数对应结果表里的哪一列（用于反向剔列）["F1"]
internal内部开关，界面不显示，由别的开关自动合成harmonicAmplitude
shell_only纯外壳概念，不写进 CSVintervalMode

4.2 单一事实源是什么意思

假设你要加一个新参数。不用改界面、不用改校验、不用改导出，只在 PARAMS 里加一条 dict(...)，然后：

  • 界面会自动多出一个控件（因为界面是遍历 PARAMS 生成的）；
  • 校验会自动检查它的类型（因为校验也读 PARAMS）；
  • params.csv 会自动多一行（因为 build_csv 也是遍历它）。
比喻 这就像餐厅的"塑封菜单"：后厨改了菜，前台、外卖平台、收银系统全跟着变， 因为大家看的都是同一张菜单。反过来，如果每个地方各抄一份，迟早会出现"菜单上有、后厨不会做"的事故。

4.3 为什么现在是"两档"而不是三档

代码里 TIERS 只有两项：novice（新手）和 advanced（进阶）。早期版本还有个"专家档"，后来并进了进阶——因为实际使用中，所谓"专家"想看的也就是那些底层阈值，没必要再分一层。旧设置里如果还存着 expert，前端会自动映射成 advanced。

4.4 原子列与汇总开关：翻译的第一层

界面上你能单独勾 H1c、H2c、A1c……但 Praat 那边只有一个总开关 harmonicAmplitude。中间这层转换由 schema 负责：

界面：勾了 H1c 和 H2c，没勾 A1c
   ↓ 数组合成
CSV：harmonicAmplitude = 1
   ↓ Praat 侧推导
实际计算：F0 和共振峰也必须算（因为算谐波幅度要用）
   ↓ initiateTable 决定写哪些列
结果表：只写 H1c H2c H4c A1c A2c A3c H2Ku H5Ku（整组，不做单列筛选）
   ↓ Python 后处理剔列
最终：真的只留下你勾的那几列

这条链路解释了很多人第一次用时的疑惑：为什么我只勾了谐波幅度，日志里却在算基频？因为在算学上，没有 F0 就找不到谐波的位置。算归算，最后写不写进表是另一回事。

4.5 三层优先级：出厂 → 预设 → 你的覆盖

settings.effective_param_defaults() 决定了界面上参数的初始值，顺序是：

  1. 出厂默认（params_schema 里的 default），比如 f0max = 400；
  2. 预设或发音人档案（男声 50–250、女声 100–400、儿童 …）；
  3. 你自己的覆盖（在设置里改过的值，存进 settings.json）。

后面的覆盖前面的。所以如果你发现界面上某个值和你记忆里的"出厂值"不一样，先去看设置里是不是存过覆盖。

这一节你该记住的 参数不是散落在各处的 if-else，而是一张被反复读取的表。 理解这一点，你就理解了为什么这个项目改功能很快、也理解了为什么改错一个 name 会全线崩。

5. 翻译：把选项写成点菜单

对应文件：ps-shell/backend/params_io.py（250 行）、server.py 的 _prepare()

界面上的值最终要变成一张三列的 CSV。列名是固定的：

variable,input,comment
inputDir,D:/samples/1,声音文件目录
outputDir,D:/samples/1/output,结果输出目录
f0min,60,基频下限
f0max,400,基频上限
...

5.1 生成逻辑只有十几行

w.writerow(["variable", "input", "comment"])
for p in schema.PARAMS:
    if p.get("shell_only"):
        continue                      # 纯外壳概念，不写给 Praat
    name = p["name"]
    val  = _normalize(p, values.get(name, p.get("default")))
    w.writerow([name, val, comment])

5.2 _normalize：四种必要的翻译

界面上的值CSV 里写成为什么
勾选 / 不勾1 / 0Praat 没有布尔类型，只认数字
4.9999999995浮点运算会留下尾巴，写进文件难看且可能被误读
目录留空path/to/tg 或 0上游脚本用这个占位值判断"用户没填"，直接写空会读错列
"60"（字符串）60（整数）避免 Praat 把数字当字符串

5.3 为什么一定要落成文件

因为 Praat 的 --run 只接受"命令行参数"，不支持结构化的 JSON；而它读 CSV 的能力是现成的、稳定的。所以文件成了两层之间唯一的接口。

比喻 护士不会隔着玻璃喊"三号床抽个血、加个肝功能"，而是写一张单子递进化验室。 单子有个好处：出了错可以回溯——到底是医生开错了，还是化验室做错了，看单子就知道。 params.csv 就是这张可以回溯的单子，它每次都留在任务临时目录里。

5.4 反方向：导入别人的 params.csv

进阶用户可能从论文附录或同事那里拿到一份 params.csv。这个文件可能是 Excel 存的，编码可能是 UTF-16、UTF-8 带 BOM、GBK；分隔符可能是逗号也可能是分号。所以读取函数 _read_text_any 会依次尝试四种编码，全都失败才退回"带替换字符的 UTF-8"。

还有一个细节：如果用户是粘贴内容而不是选文件，内容往往没有表头。而通用解析器会无条件跳过第一行——结果第一个参数就被吃掉了。所以 parse_csv_text_ex 会先探测首行第一格是不是 variable，不是就补一行假表头。

这段代码教给你的事 "健壮"不是写一堆 try/except，而是把真实世界里会出现的脏数据逐条列出来，每条给一个确定的处理方式。 这段代码的注释里甚至写明了是哪次验收发现的回归（"粘贴 f0min,60 时 f0min 丢失"）。

6. Praat 怎么读懂这张单子

对应文件：scripts/read_params.praat（约 300 行）

Praat 侧读参数的写法非常朴素——按名字查表：

Read Table from comma-separated file: .file$
inputDirID = Search column: "variable", "inputDir"
.inputDir$ = Get value: inputDirID, "input"

这三行意味着三件事：

  • 列的顺序无所谓——它按名字找，不按位置；
  • 多出来的行无所谓——这正是为什么生成的 CSV 有 96 行、上游只有 56 行也能跑；
  • 少一行就出事——Search column 找不到会返回 0，接着 Get value: 0 直接让整个脚本崩掉，而且报错信息往往只有一句 "Not completed"。
一个真实踩过的坑 早期版本漏写过 cpps 这一行，结果整批任务在读取参数阶段就崩了。 所以现在有一条硬规矩：params.csv 必须包含 schema 里的每一行，宁可多写不可少写。

6.1 隐式依赖：Praat 会自己"补课"

这是 read_params.praat 里最值得读的一段：

.measureFormants = .formant + .harmonicAmplitude + .harmonicAmplitudeUncorrected +
  ... .bw + .bwHawksMiller + .slope + .slopeUncorrected

.measurePitch = .pitch + .harmonicAmplitude + .harmonicAmplitudeUncorrected +
  ... .slope + .slopeUncorrected + .bw + .bwHawksMiller + .soe

翻成人话：

  • 只要你勾了谐波幅度、频谱斜率、带宽或 SoE 中的任何一个，它就必须算 F0；
  • 只要你勾了谐波幅度或斜率，它就必须算共振峰。

这不是冗余，是数学上的必要：谐波幅度是"第几号谐波相对 F0 有多高"，没有 F0 就没有谐波的坐标。

6.2 算归算，写不写是另一回事

Praat 算了 F0，但如果你没勾 F0，结果表里不会多出 f0 列——因为写表头的时候看的是 params.pitch，不是 measurePitch。这两个变量名字很像，含义完全不同：

变量含义影响什么
params.pitch用户要不要 输出 f0 这一列表头、结果表
params.measurePitch这一批需不需要算 F0计算流程（可能因为别的参数被迫算）
这一节你该记住的 "用户想要的"和"计算必需的"是两件事。好的设计会把它们分开命名、分开使用。 混用这两个概念，就会出现"没勾 F0 却有 f0 列"或者"勾了 SoE 却算不出东西"的怪现象。

7. 批量执行：一个任务的完整生命周期

对应文件：ps-shell/backend/server.py，核心是 _prepare()（200–289 行）与 _execute()（420–625 行）

点下"开始批量"之后，后台不是直接调 Praat，而是先建一张"任务单"。这个任务单是个 Python 对象：

class Job:
    id           # 任务编号，也是临时目录名
    status       # running / done / error / cancelled
    progress     # {"done": 12, "total": 40, "current": "13.wav"}
    log          # 一行行日志（界面日志框就是它的镜像）
    result_path  # 最终 out.tsv 的路径
    stop_event   # 一个"取消"开关，Praat 进程靠它被杀掉

7.1 _prepare：开跑前的六件杂事

这六件事都不起眼，但少一件就会出问题：

#做什么为什么必须做
1找到 praat.exe 和脚本目录路径可能来自设置、程序根目录、或自动探测
2建任务临时目录 %TEMP%\PraatSauceShell\<jobid>params.csv、filelist、进度文件都放这儿，不污染你的数据目录
3如果存在 Resample/ 子目录，把工作目录切过去否则原始 wav 和重采样副本会被同时扫进来，同名文件互相覆盖
4补默认路径：输出 → <音频>/output；中间对象 → <音频>不补的话 Praat 会把结果写到它自己的工作目录，后台却去音频目录找，表现为"算完了但没有结果"
5给每个 wav 建 measure/ 子目录Praat 自己不会建目录，父目录不存在时 Save as text file 直接失败
6删掉 0 字节的 .Pitch/.Formant这些是上次跑到一半手动停止留下的残骸；留着会被"读回"逻辑当成有效文件，结果整列空白
比喻 这就像手术前的"术前准备清单"：核对器械、铺台、给病人编号、把上一台留下的垃圾清掉。 任何一项偷懒，台上就会出问题，而且出的问题往往看起来像"技术不行"，其实是准备没做。

7.2 进度条为什么要"走后门"

这是整个项目里最值得学的一个技巧。

Praat 每处理一个文件会打印一行 Processing 13.wav。理论上后台读这行就能更新进度条。但实际不行——Praat 的输出在管道里是全缓冲的：所有行要等进程结束才一次性吐出来。于是进度条会从 0% 卡到 100%，中间毫无反馈。

解决办法不是去改 Praat，而是让它写文件：

# praatSauce.praat 里加的第二参数
appendFile: progressloc$, thisWav$ + newline$

# Python 侧起一个线程，每 0.4 秒读一次这个文件
def watch_progress():
    seen = 0
    while not stop_watch.is_set():
        names = 读 ps_progress.txt 的所有行
        if len(names) > seen:
            for n in names[seen:]:
                job.add_log("Processing " + n)
            seen = len(names)
            job.progress["done"] = min(seen, job.progress["total"])
        stop_watch.wait(0.4)

为什么文件行、管道不行？因为文件写入默认是不缓冲的（每次 append 立即落盘），而管道有 4KB 左右的缓冲区。换个通道，问题就没了。

7.3 怎么跟 Praat 说话

cmd = [exe]
if full_trust:
    cmd.append("--FULL-TRUST")     # Praat 7 默认禁止脚本写文件
cmd += ["--run", script] + [str(a) for a in args]
  • --run：批处理模式，不弹任何窗口。GUI 里跑脚本用的是另一套参数（--new-send），混用会失败。
  • --FULL-TRUST：Praat 7 把"脚本存文件"视为危险动作，不加这个会直接报错退出。

启动进程后，后台开两个线程分别读 stdout 和 stderr，因为 Praat 的这两个通道编码还不一样：stdout 带 UTF-16 BOM，stderr 常常是不带 BOM 的 UTF-16。判断逻辑是"先看 BOM，再看奇数位是不是大量为 0"：

if chunk[:2] in (b"\xff\xfe", b"\xfe\xff"): return "utf-16"
odd_zeros = sum(1 for i in range(1, len(sample), 2) if sample[i] == 0)
if odd_zeros >= len(sample) // 4: return "utf-16-le"
return "utf-8"
为什么要用增量解码器 一个汉字的 UTF-16 是两个字节，网络/管道读到的块可能正好切在中间。 如果用普通的 decode()，这个半字符就会变成乱码。 codecs.getincrementaldecoder() 会把没读完的半个字符留到下一块，这就是"流式解码"。

7.4 结果"新鲜度"校验：一个反直觉的细节

Praat 跑完，后台要去确认"结果文件真的生成了"。直觉写法是 os.path.exists(result_path)，但这个项目用的是：

fresh = os.path.getmtime(result_path) > job.started
if not fresh:
    job.status = "error"
    job.error = "Praat 没有生成结果文件..."

为什么？因为跑之前会归档上一版结果，而归档用的是"复制"不是"移动"——Praat 失败时，旧结果还躺在原地。这时候 exists 一定是 True，界面就会显示"成功"，而你看到的是上一次的数据。这是最危险的一类 bug：静默地给你错的东西。

用"修改时间晚于任务开始时间"来判断，就绕开了这个陷阱。归档用复制而不是移动，也是同一个考虑：宁可多占一点磁盘，也不能在失败时把上一版弄丢。

7.5 跑完之后还要做三件事

动作做什么为什么不在 Praat 里做
SHR 补算读结果表，按公式补一列 SHR上游脚本没有这个测量，改它不如在外面加
剔列把没勾的 F4/F5/B4/B5/HNR* 等列删掉Praat 为了算别的参数可能多算了几列，但用户不想看到
舍入时间列不动；HNR、CPP 两位小数；其余一位Praat 输出的是十几位浮点，直接给你反而难读

7.6 两种"看起来成功、其实是失败"

  1. 0 行：Praat 正常退出，但表里只有表头。最常见的原因是目录里没有音频，或者 TextGrid 标签正则把所有区间都滤掉了。后台会附一句诊断："本次声音文件 N 个；TextGrid 目录里找到 M 个"。
  2. f0 和 F1 检出率都是 0：说明整批都没测到，几乎一定是基频范围设错了（比如给男声设了 100–400）。这种情况会直接在最上面插一条红色诊断。
这一节你该记住的 一个可靠的批处理程序，功夫都在"开跑前"和"跑完后"： 开跑前把环境准备到不可能失败，跑完后用独立证据（文件时间、行数、检出率）验证结果， 而不是相信"进程退出码是 0"。

8. Praat 内部：一个音频怎么被拆开测

对应文件：scripts/praatSauce.praat（约 500 行）+ 19 个被 include 的零件脚本

主脚本本身不长，它更像一个"总装线"：开头把 19 个过程脚本拼进来，然后读参数、写表头、循环文件、循环区间、拼表。

include read_params.praat
include get_times.praat
include get_formants.praat
include get_pitch.praat
include get_spectralMeasures.praat
... 共 19 个

8.1 先写表头，再干活

第一件事不是读音频，而是把表头写进结果文件：

@initiateTable: params.pitch, params.formant, ... params.useTextGrid

initiateTable 按你勾的测量项拼出一行列名，存成一个只有表头的 tsv。列的顺序是固定的：

file [label intervaldID] t f0 F1 F2 F3 H1c H2c H4c ... CPP CPPS HNR05 ... intensity soe
一个看似无聊、其实很聪明的设计 先写表头，意味着任何中途崩溃都会留下"表头正确、0 行"的文件。 你一看就知道：参数读进来了、表头拼对了，问题出在后面的计算或文件读取。 如果反过来"算完再写表头"，崩溃时你连一个文件都看不到，什么线索都没有。

另外，intervaldID 这个拼写（多一个 d）是上游原样保留的。 别去"修正"它——改了之后，所有按列名读取的旧脚本都会失效。

8.2 两层循环

for thisFile from 1 to numFile          # 外层：每个音频
    snd = Read from file: ...
    @times: ...                          # 决定这段音频要测哪几刀

    for int from 1 to times.numIntervals # 内层：每个标注段
        ... 八种测量 ...
    endfor
endfor

不用 TextGrid 时，times.numIntervals 恒等于 1，也就是"整段算一刀"。这样上层代码不用写两套逻辑。

8.3 @times：这段录音要测哪几刀

get_times.praat 做三件事：

  1. 按音频文件名找同名 .TextGrid；
  2. 用正则筛出你要的标签（includeTheseLabels）；
  3. 把所有选中区间的起点、终点、标签各取出来，变成三个数组。

这里有一个上游没有、本项目加的重要行为：找不到 TextGrid 就测整段，而不是整批中止。上游的做法是"TextGrid 数量和音频数量不一致就退出"，这在实际调查里几乎必然发生（有些字没做标注）。现在的做法是逐文件判断，最后打印一句总结：

PSA_TG_SUMMARY 38 file(s) measured on TextGrid intervals, 2 file(s) measured over the whole sound.
比喻 times 就像切菜前的"下刀位置表"。有标注的人，按标注下刀；没标注的人，整根下锅。 关键是不能因为一个人没标注，就让整桌菜都不做了。

8.4 八种测量：各自交出一串数

测量脚本交出什么
基频 F0get_pitch.praat每帧的 f0 值 + 每帧的时间
共振峰get_formants.praatF1/F2/F3（可选 F4/F5）与带宽 B1–B3
谐噪比get_HNR.praat五个频带的 HNR（0.5k / 1.5k / 2.5k / 3.5k / 3.8k）
CPPget_CPP.praat倒谱峰值突显
CPPSps_get_CPPS.praat平滑后的 CPP
强度get_intensity.praat每帧 RMS 强度
谐波幅度/斜率get_spectralMeasures.praatH1/H2/H4/A1/A2/A3 及各种差值
SoEget_SoE.praat激励强度

每个过程都遵守同一个约定：返回一个向量（一串数）和一个帧数，外加一个时间向量。这个约定是后面能"对齐"的前提。

8.5 对齐：整章最关键的二十行

问题：不同测量的时间网格不一样。F0 每 5 毫秒一个点；HNR 可能起点晚一点、点数少一点；如果共振峰分析窗更长，它的第一帧可能落在 8 毫秒处。如果直接把几条序列首尾一拼，第 100 行的 f0 和第 100 行的 HNR 可能根本不是同一时刻。

做法分三步：

## 1. 先问所有测量：你一共几帧？取最大值
mostFrames = max(frameNums#)
firstFrame = min(firstFrame#)
lastFrame  = max(lastFrame#)

## 2. 以帧数最多的那条序列的时间轴为准

## 3. 短的序列：前面补、后面补，补到一样长
@zeroPadding: pitch.f0#, pitch.numFrames, mostFrames, pitch.times#, ...
比喻 一支合唱队，有人从第 1 拍开始唱，有人从第 3 拍才进，还有人提前收声。 要录成一条整齐的音轨，就得先确定"总共多少拍"，然后给晚进的人前面补静音、给早退的人后面补静音。 补的这个"静音"就是 undefined。

8.6 为什么补 undefined 而不是补 0

这是 zeroPadding.praat 里被本项目专门改过的一处，值得逐行读：

### 本项目补丁（2026-10-18）：补位值由 0 改为 undefined（= NaN）。
### 0 同时是合法测量值（谱幅度 0 dB、SoE 0 等），下游无法区分
### 「这一帧没测到」与「真测到 0」，补出来的 0 会被统计当成真实值拉低均值。

padStart# = zero#( round(diffFrames) ) * undefined   # 0 × NaN = NaN

三个技术细节，都是踩过坑才有的：

  • Praat 没有 undefined#(n) 这种写法，所以用 zero#(n) * undefined 造出 n 个缺失值；
  • zero#(0) 会直接报错，所以补位前必须先判断个数大于 0；
  • 写进文件时，缺失值会变成 --undefined--，而 0 还是 0。读取时要靠 _to_float() 把前者认成空。
为什么这件事值得你花五分钟理解 在实验语音学里，"没测到"和"测到 0"是两种完全不同的信息。 一个 0 dB 的谐波幅度是真实存在的（虽然罕见），一个因为静音而没测到的帧则是缺失。 如果你把它们都写成 0，均值会被拉低、标准差会变大、画出来的曲线会在静音处突然掉到 0—— 而这些错误不会报错，只会让你的结论慢慢偏掉。

这是"数据清洗"里最基础也最容易被忽略的一条：缺失值必须有自己的表示法。

8.7 拼表：从几条向量到一张长表

Create simple Matrix from values: "results", { times# }   # 先放时间列
@combineMatrices: { f0# }                                  # 一列一列往上拼
@combineMatrices: { f1#, f2#, f3# }
...
@prepareTable: thisWav$, params.outputDir$, params.outputFile$, params.useTextGrid, ...

prepareTable 做的事很"笨"但很稳：把矩阵转置、转成表、给每一行填上文件名（和标签、段号），然后追加到结果文件末尾。

因为是追加，所以结果文件是"长表"：一个文件有 300 帧，就有 300 行；10 个文件就是 3000 行。这也是为什么后面的统计要按 file 分组。

8.8 收尾

循环结束后，脚本打印一句总结，然后退出。就这么多——它不负责画图、不负责诊断、不负责告诉你"这个参数可能设错了"。那些都是后台的事。

这一节你该记住的 Praat 脚本的核心不是"怎么算"，而是怎么把不同来源、不同长度的序列，拼成一张每行都对齐的表。 对齐靠三样东西：统一的帧数（mostFrames）、统一的时间轴、以及一个诚实的缺失值。

9. 结果层：怎么判断测得准不准

对应文件：ps-shell/backend/results.py（约 520 行）

Praat 只会算数，不会怀疑自己。判断"这批数据能不能用"是后台的责任。

9.1 只读前 200 行

结果表可能几万行。界面上只显示前 200 行（试跑时 5000 行，因为要画完整曲线）。这不是偷懒，是避免浏览器被几万个单元格卡死。

9.2 检出率：这个软件最核心的一个指标

ratio = 有值的帧数 / 总帧数

它回答的问题是：我设的参数，到底覆盖了多大的范围？

  • F0 检出率 95%：参数设得很合适；
  • F0 检出率 30%：要么范围太窄，要么这段录音大部分是清音/噪声；
  • F0 检出率 0%：基本一定是范围反了（比如给男声设 200–400）。

9.3 静音段必须排除，否则会冤枉你

SILENCE_LABELS = {"sil", "silence", "sp", "pau", "#", ""}

假设一段 10 秒的录音，前后各 2 秒静音。静音段当然测不到 F0。如果把静音也算进分母，F0 检出率最高也只有 60%，程序就会报"基频检出率偏低"，你被误导去改参数——越改越糟。

所以统计检出率时，分母只算有效语音段。这条规则在 2026-10-18 被明确写进代码，注释里还留着实测记录：不排除时 15 个文件全被点名，实际目标段检出率是 87–98%。

9.4 怎么判断"这个文件有问题"

bad = [p for p in per_file
       if p["f0Ratio"] is not None and p["f0Ratio"] < 0.35]

但光看 35% 还不够——如果整批都只有 30%，那不是某个文件的问题，是参数的问题。所以还要加一个相对条件：

文件级异常 = 检出率 < 35%  且  低于批内中位数 × 0.6
比喻 一个班考试，判断"谁考砸了"不能只看绝对分。 如果全班平均 40 分，那 35 分不算砸，是卷子太难； 如果全班平均 90 分，那 50 分就是明显异常。 所以既看绝对线，也看"跟同批人比"。

9.5 参数建议是算出来的，不是写死的

if s["median"] >= f0max * 0.92:
    "基频中位数已经接近上限，把上限提到 median × 1.4 左右再试"
if s["median"] <= f0min * 1.08:
    "基频中位数贴近下限，把下限降到 median × 0.6 左右再试"

这就是为什么诊断读起来像有个人在看你的数据——它确实在算：拿你这次的中位数，去比你设的上下限。

9.6 0 与 undefined 的分工

在文件里含义统计时
0测到了，值就是 0算进均值、算进检出率
--undefined--这一帧没测到跳过，不算均值也不算检出
空旧版本或外部文件的缺失写法同 undefined
这一节你该记住的 任何测量工具都要回答一个问题："测不出来"怎么表示？ 这个软件的回答是 undefined，并且把"静音不算失败""同批比较"写进了诊断逻辑。 这两条你以后自己做数据分析时可以直接搬。

10. 复核：九宫格与人工修正

对应文件：review_grid.py（约 1700 行）、review_build.praat、review_export.praat、review_export.py、review_choice.py

10.1 为什么非要人工看一眼

自动算法会犯两类错，而且都很常见：

  • F0 差一个八度：真实 220 Hz 被算成 110 Hz（漏掉一半周期），曲线看起来"很平滑"，但在表里就是错的值；
  • 共振峰串位：F1 被噪声顶到 1100 Hz，或者 F1/F2 糊成一个峰。

这两类错在 5000 行的表里完全看不出来，但在曲线上一眼就能认出来。所以第 4 步的存在不是"锦上添花"，而是数据质量控制的必经环节。

10.2 九宫格：先粗看一遍

build_grid() 一次处理一页 9 个文件（size=9），做三件事：

  1. 列出目录下所有 wav，按页切片；
  2. 动态生成一个一次性 Praat 脚本——把这 9 个文件的路径直接写进脚本里；
  3. 读回生成的 .Pitch/.Formant 文本，转成 JSON 点序列，每个文件最多保留 320 个点。
MAX_POINTS = 320        # 每个文件最多回传 320 个点

为什么要降采样？一个 3 秒的文件按 5 毫秒一帧是 600 个点，9 个文件就是 5400 个点；如果原样传给浏览器，画图会卡。320 个点足够看出"有没有差八度"，又不至于拖慢界面。

为什么是"动态生成脚本"而不是"传一个文件清单" 因为 Praat 读清单的语法很脆弱（分隔符、空行、编码都可能出问题）。 而"把 9 个路径直接写进脚本"是最笨也最不容易出错的做法。 这个项目在别处用清单（workList），在这里用生成脚本——同一个问题，选最稳的那种解法。

10.3 单文件详情：一次生成 23 组候选

点开某一个格子，进入详情页。这时走的是另一条路：review_build.praat。

# Pitch：扫 3 档上限
for pIndex to 3        # 400 / 500 / 600
    To Pitch (filtered autocorrelation): 0.0, 75, ceil, 15, 0, 0.03, ...
    Save as text file: outDir$ + "/pitch_" + string$(ceil) + ".pitch"
endfor

# Formant：5 档上限 × 4 档数量 = 20 组
for fIndex to 5        # 4977 / 5232 / 5500 / 5782 / 6078
    for nIndex to 4    # 4 / 5 / 6 / 7
        To Formant (burg): 0.0, nF, fceil, 0.025, 50
    endfor
endfor

为什么要连"数量"一起扫？因为 Praat 手册明确说 maxNumberOfFormants 和 formant ceiling 是一对参数。LPC 阶数 = 2 × 数量，数量选 4，F1/F2 会糊成一个包络峰，实测 F1 会虚高到 1100 Hz 以上。手册推荐值是 5。

代码里的那段警告值得一读 脚本注释里写着：曾经把参数顺序写错成 "0.0, 5, 0, 0.025, ceil"， 结果 maximumFormant=0、preEmphasis=ceil， 共振峰退化成 6000–19000 Hz 的无意义值。 Praat 不会因为你参数写错就报错，它会安静地给你垃圾。 这也是为什么这个项目到处都在强调"实测"和"存盘后核对"。

10.4 三条人工修正路线

路线怎么做适合什么情况
点图改 F0在曲线上加点、删点、撤销；手工点用深紫色标出个别帧差八度、或者清浊判断错了
FormantPath 编辑器对 9 档 ceiling 逐段打分，自动挑最优组合整段共振峰都串位（常见于鼻化、儿化）
在 Praat 里修周期打开 GUI，用 Pulses 手工标周期，存盘后读回噪声大、算法完全跟不上

10.5 落盘：为什么最后是在 Python 里改文本

这是整个项目最"野蛮"也最精彩的一处。

需求是：用户改了几个 F0 点，要把这些点写进 .Pitch 对象，好让后续批量测量直接用。正常思路是让 Praat 去改，但实测 Praat 7 的 Pitch 对象没有任何逐帧修改命令：

Set value at time / To PitchTier / Shift / Set value in frame
→ 全部报 "not available for current selection"

于是作者换了一条路：直接改 .Pitch 这个文本文件。Pitch 对象存成文本时长这样：

frames [1]:
    candidates [1]:
        frequency = 123.456
    candidates [2]:
        frequency = 246.912

后端用正则找到"离修正点最近的那一帧"，把 candidates[1] 的 frequency 改掉。改完的文件，Praat 下次读进来就是修正后的值。

比喻 你想改一张已打印的表格，但打印机不支持修改。于是你直接打开源文件改，再重新打印。 这不是"绕过问题"，而是找到真正的数据源头——对象文件就是源头，Praat 只是它的一个读写器。

这里还有一条通用教训，代码注释里写得很清楚：

## nocheck 前缀是"命令不可用时静默跳过"，
## 所以不能用它判断命令是否存在——必须去掉 nocheck 跑一次，
## 看是否报 "not available for current selection"。

10.6 measure/ 是整条流水线的数据总线

<wav 所在目录>/measure/<主名>.Pitch
<wav 所在目录>/measure/<主名>.Formant

四个环节都围着这个目录转：

环节动作说明
批量测量写勾了"保存中间文件"时，把算出的对象存进来
九宫格读有就直接展示，不重算（reuse=True）
审核落盘写人工修正后的对象覆盖进来
导出序列读F0、F1–F5 从对象里取，比汇总表更全

有一个真实的坑，注释里记着：当音频在子目录里时，measure/ 必须插在主名之前，而不是加在目录后面：

对：<input>/sub/measure/11.Pitch
错：<input>/measure/sub/11.Pitch     # 顺序反了，两处代码就找不到同一个文件
这一节你该记住的 中间结果（对象文件）不是"缓存"，而是流水线上的半成品。 把它当正式产物来管理——统一命名、统一目录、写入前建目录、读回时校验—— 你才能做到"审完不用重算"，也才能在换参数时清楚地知道哪些要重做。

11. 导出：最后一道工序

对应文件：ps-shell/backend/series_export.py（约 1200 行）

导出看起来简单，实际是整个项目里分支最多的模块。因为它要回答三个正交的问题：

11.1 数据从哪来（两个源）

源有什么没有什么
汇总表 out.tsv谐波幅度、斜率、HNR、CPP、CPPS、强度、SoEF4/F5、B4/B5（上游只写 F1–F3/B1–B3）
对象文件 .Pitch/.FormantF0、F1–F5、B1–B5谐波、噪声类

所以导出时是"两边各取一部分，拼成一张表"。这也是为什么导出页的提示会写"缺哪一类，那几列就是空的"。

11.2 时间怎么取（三种重采样）

方式做法适合
raw原样，Praat 的帧网格（约 5 ms 一帧）要做生长曲线、需要最大信息量
smooth先小窗平滑（只在浊音段内，不跨静音缝），再等间隔降采样画曲线、看趋势
interval按固定间隔（如 10 ms）线性插值取点不同文件要对齐到同一时间轴

11.3 文件怎么排（四种布局）

布局结构适合
single一张长表：file, time_s, 参数…R / Python 最好读
per_audio每个音频一张宽表（time_s × 参数）逐个检查
per_param每个参数一张跨音频长表单参数建模
xlsx一个工作簿，每参数一页 + 说明页给不写代码的合作者
两个不起眼但很要命的细节 1. 所有 CSV 都写成 UTF-8 带 BOM。不带 BOM 的话，Excel 双击打开中文列名会乱码。
2. 对象里没有的参数写空，不写 0。比如 3 阶 Formant 没有 F4，如果写 0，你以后做统计会把 0 当成真实测量值。

12. 把整条链路串起来

现在把前面九节连成一条线。跟着一个具体的文件 11.wav 走一遍：

站谁在做拿到什么交出什么存在哪
1界面（第 1 步）你选的文件夹文件清单、时长、采样率内存
2界面（第 2 步）预设 + 你的勾选一个 values 字典内存 + settings.json
3后台 _preparevalues 字典params.csv + 建好的 measure/ 目录%TEMP%\PraatSauceShell\<jobid>\
4后台 _executeparams.csv启动 praat.exe 子进程—
5Praatparams.csv + 11.wav + 11.TextGrid每个标注段若干行测量值<音频>/output/out.tsv
6Praat（可选）同上11.Pitch / 11.Formant<音频>/measure/
7后台后处理out.tsv补 SHR、剔列、舍入原地改 out.tsv
8后台 results.pyout.tsv前 200 行 + 检出率 + 诊断内存 → 界面
9九宫格measure/ 里的对象9 个文件的曲线 JSON内存 → 界面
10审核落盘你的修正点改写后的 .Pitch<音频>/measure/
11导出out.tsv + 对象文件CSV / XLSX你选的输出目录

12.1 三个"回流"

上面这条线不是单向的，有三处会往回走：

  1. 诊断 → 参数：第 3 步的检出率告诉你"基频上限太低"，你回到第 2 步改参数再跑。这是最常见的一次回流。
  2. 审核 → 批量：第 4 步人工修正后的对象存进 measure/，下次批量勾上"复用中间文件"，Praat 就不再重算。这条回流是"审完不用重来"的关键。
  3. 导出 → 批量：导出时发现 F4/F5 是空的，说明当初没勾；回第 2 步勾上重跑。
比喻 这不是一条传送带，而是一个带返工的车间： 粗加工（批量）→ 质检（诊断）→ 精修（审核）→ 出厂（导出）。 精修过的零件放回半成品库（measure/），下一批直接取用，不用重新铸造。

这一节是给"想借这个项目提升代码水平"的读者准备的。每条都能在代码里找到对应位置。

#套路在哪解决什么问题

13.1 如果只学三条

  1. 单一事实源：凡是"同一件事写在两个地方"的设计，迟早会不一致。把它合并成一处，是投入产出比最高的重构。
  2. 用独立证据验证结果：不要相信"进程退出码 0"、"文件存在"、"接口返回 200"。要找一个只有成功才会出现的证据（文件修改时间、行数、检出率）。
  3. 缺失值要有自己的表示：0、空字符串、NULL 混用，是数据类 bug 的第一大来源。

15. 读代码发现的两处值得注意

按你的习惯，我把读代码时看到的疑点如实列出来，没有擅自修改。

15.1 源码态下，审核落盘可能找不到脚本

ps-shell/backend/review_export.py 第 42–48 行

if settings.IS_FROZEN:
    SCRIPT = os.path.join(settings.APP_BASE, "scripts", "review_export.praat")
else:
    SCRIPT = os.path.join(
        os.path.dirname(os.path.dirname(os.path.abspath(__file__))),
        "praat", "review_export.praat",
    )

os.path.dirname(os.path.dirname(__file__)) 是 ps-shell/，所以源码态拼出来的是 ps-shell/praat/review_export.praat。但仓库里没有 ps-shell/praat/ 这个目录，脚本实际在仓库根的 scripts/ 下。

冻结态（打包后）是正确的：APP_BASE/scripts/。所以这个问题只在"源码态直接跑、并且点了审核落盘"时出现。

建议的修法（未改）：让它和别处一致，走 settings.resolve_script_dir()，或者非冻结态指向 <仓库根>/scripts/。

15.2 生成的 params.csv 比上游多 40 行

params_schema.PARAMS 有 97 条定义，去掉 1 个纯外壳概念后，实际写进 params.csv 的是 96 行；而上游自带的 params.csv 只有 56 行参数。

多出来的是界面用的"原子列"（比如 ha_h1c、sl_h1h2c），Praat 侧按名字查表，用不到就忽略，不影响结果。副作用只有一个：文件更长，排查时容易误以为"参数变多了"。

如果要收紧，可以给这些原子列加 shell_only=True，让 build_csv 跳过它们。这属于优化，不是 bug。

为什么把这两条写出来 读别人的代码，最容易犯的错是"看到不一致就以为是 bug"，或者反过来"跑通了就以为都对"。 这两条一条是真实缺陷（限定在源码态），一条只是冗余。 分清这两类，比找出问题本身更重要。

16. 小词典

词在这套系统里指什么
params.csv两层之间唯一的接口。三列：变量名、值、注释。Praat 按名字查表读取。
.Pitch / .FormantPraat 的对象文件（文本格式），存的是逐帧的基频/共振峰。既是中间产物，也是审核对象。
measure/放对象文件的子目录，位于每个音频所在目录下。整条流水线的"半成品库"。
out.tsv批量测量的汇总表，制表符分隔，一行 = 一帧。R/Python 可直接读。
TextGridPraat 的标注文件。这套系统用它决定"一段录音要测哪几刀"。
检出率有值的帧 ÷ 有效语音帧。判断参数是否合适的第一指标。
ceiling（上限）基频上限 / 共振峰上限。设低了会漏，设高了会引入噪声。
LPC 阶数= 2 × 共振峰数量。数量选错，F1/F2 会糊在一起。
undefined"这一帧没测到"。文件里写作 --undefined--，统计时跳过，与 0 严格区分。
试跑（preview）只跑一个文件，用来确认参数。结果写在临时目录，不污染正式输出。
